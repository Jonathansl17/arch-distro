# Theme 8: I/O and devices · Owner: Jennifer López Miranda

## 1. What was implemented

- **Module blacklist** (`modprobe/ad-blacklist.conf` →
  `/usr/lib/modprobe.d/`). `pcspkr` (PC speaker beep, no use in a VM or
  laptop) and `joydev` (legacy `/dev/input/js*`, everything modern uses
  evdev). `blacklist` stops automatic loading by alias (udev). An explicit
  `modprobe pcspkr` still works.
- **Own udev rule** (`udev/90-ad-usb-storage.rules`). When a USB disk
  appears (`SUBSYSTEM=="block"`, `ID_BUS=="usb"`, `DEVTYPE=="disk"`) it asks
  systemd to start `ad-usb-event@<kernel name>.service` through
  `SYSTEMD_WANTS`. udev kills long `RUN+=` programs, so the work goes to a
  unit. The unit runs `ad-usb-event.sh`, which reads vendor, model, size and
  driver from sysfs and appends to `/var/log/arch-distro/usb-events.log`. On
  removal the rule logs to the journal with `logger`.
- `ad-dev` (`bin/ad-dev`): PCI devices with the bound driver (sysfs
  `driver` symlink), top interrupt lines, `irqdiff CMD` (per-IRQ delta while
  a command runs), `mod NAME` (modinfo + refcount from `/proc/modules`), `usb`.
- `ad-info` shows GPU and NPU (PCI class 0x03 and 0x12) with their driver.

## 2. Operating systems concept

- I/O hardware, interrupts, device drivers, kernel I/O subsystem.
  Silberschatz et al. 10th ed., ch. 12 (I/O Systems). OSTEP ch. 36 (I/O devices).
- The kernel exposes devices through **sysfs** (`/sys/bus/pci/devices/*`:
  class, vendor, device, driver), loads drivers as **modules** matched by
  `modalias`, and **udev** reacts to the kernel's uevents (netlink) to create
  `/dev` nodes and run rules.
- **GPU/NPU (Unit 1):** in the VM the GPU is a virtual device (`virtio-gpu`
  → `virtio_gpu` DRM driver, or QXL → `qxl`). On the host the drivers are
  `amdgpu` and `nvidia`. No NPU is present (no class 0x12 device), and
  `ad-info` says so. On machines with one, the driver would be `amdxdna` or
  `intel_vpu`, exposed under `/sys/class/accel`. The driver is what turns
  the device into kernel interfaces (DRM, accel) that user space can use.

## 3. Measurement method

```sh
experiments/exp-08-dev.sh     # plug a USB device during the 30 s window it announces
```

1. `lsmod`, `modinfo dummy`, `modprobe dummy`, `modprobe -r dummy`.
2. `modprobe --showconfig | grep blacklist`, `lsmod` shows the blacklisted modules are not loaded.
3. `lspci -k` and `ad-info`.
4. `ad-dev irqdiff dd if=/dev/zero of=/var/tmp/ad-io-test bs=1M count=1024 oflag=direct`.
5. `udevadm monitor --udev --kernel --subsystem-match=block` for 30 s while
   plugging, then `dmesg` and `ad-dev usb`.

## 5. Interpretation

- **Modules are loaded on demand.** `dummy` was not in memory until
  `modprobe` asked for it, and `modprobe -r` could remove it because its
  refcount was 0 (nothing was using it). The signature fields show the
  kernel only loads modules signed with the key generated when the kernel
  was built.
- **The blacklist works at the alias level.** udev loads drivers by
  matching a device's `modalias` against module aliases. `blacklist pcspkr`
  removes that alias match, so the module is never loaded automatically,
  which `lsmod` confirms. An explicit `modprobe pcspkr` would still load it,
  because the blacklist only affects aliases.
- **Where the I/O interrupts come from.** The virtio-blk disk has 6 request
  queues, one per vCPU, each with its own MSI-X vector. That is why the
  interrupts are spread over `req.0` to `req.5` instead of a single line:
  each CPU submits to its own queue and gets the completion interrupt back
  on that queue. The device raises an interrupt when requests complete, and
  `oflag=direct` makes every 1 MiB write a real request to the device, so
  the disk queues dominate the table. 3653 interrupts for 1024 writes means
  each 1 MiB write reached the device as several smaller requests (the
  block layer splits a request larger than the device's maximum size) or
  that completions were not coalesced. The local timer (LOC) grows just
  from the time passing, and CAL/RES are inter-processor interrupts: one
  CPU waking or asking work of another, which happens when completions land
  on a different CPU than the waiting `dd`.
- **The USB chain, layer by layer.** `xhci_hcd` (the USB host controller
  driver) enumerates the device and reads its descriptors, `usb-storage`
  claims it as mass storage, the SCSI layer sees a direct-access disk, and
  `sd` creates `/dev/sda`. Only then does udev get the `add` event for the
  block device with `ID_BUS=usb`, which matches the rule and starts
  `ad-usb-event@sda.service`, which wrote the log line. Since the device was
  virtual, vendor and model say QEMU, but every kernel layer and the udev
  rule ran exactly as with a physical stick.
- **GPU and NPU (Unit 1).** The VM's GPU is a paravirtual device: the guest
  sends drawing commands to QEMU through virtqueues instead of driving real
  hardware. `virtio-pci` handles the PCI transport and `virtio_gpu` is the
  DRM driver that exposes `/dev/dri/card*` to the display server. On the
  host, `amdgpu` and `nvidia` play that DRM role for real hardware. There is
  no NPU, so there is no `/sys/class/accel` device. On a machine with one,
  the `amdxdna` or `intel_vpu` driver would expose it there.
